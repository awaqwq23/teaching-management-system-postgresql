# 高校教学管理系统成员分工与总结

## 1. 组织形式与真实状态

任务书要求 2—3 人组队、明确每名成员分工，并由每位成员掌握项目核心内容。当前材料按独立原型整理，尚无真实小组名单和可核验的多人协作记录，因此不能将其表述为已经满足正式组队要求。

本文件不虚构成员姓名、学号、审核人或多人贡献。正式提交前须由实际参与者补充真实成员与模块的对应关系，并据真实记录说明贡献；如最终仍为个人项目，应先取得教师对组织形式的认可。当前的模块责任划分用于说明交付责任，不等于已发生的小组分工。

## 3. 设计成果与关键取舍

本原型采用高校教学管理场景，以六表表达院系、学生、教师、课程、教学班和选课。课程与教学班分离，支持同一课程多次开设；学生与教学班的多对多联系由联合主键选课表表达，成绩和时间属于该联系。

业务编号使用非空唯一约束，代理 ID 用于稳定引用。邮箱可空且非空值唯一，但不能当作全体学生的候选键。全部外键使用 `ON DELETE RESTRICT`，删除学生或基础资料时不默默清除选课和成绩；键更新采用现有 SQL 的默认 `NO ACTION`。

选课容量控制采用数据库触发器中的条件原子更新。人数缓存为并发占位提供同一教学班行上的协调点，同时引入与选课明细的跨表冗余。该冗余不能靠 3NF 结论或单行 `CHECK` 消除，因此实际 SQL 使用 `trg_verify_enrollment_count` 延迟约束触发器，在提交时强制比对真实人数并拒绝不一致事务；聚合审计作为额外复核。批量选课按教学班 ID 升序执行，任一项失败整体回滚。

项目只禁止同一学生重复选择同一教学班，不额外禁止跨学期重修或同学期选择同课程不同班。课表、先修、学分上限、成绩历史、登录认证及角色权限均未纳入本轮原型。CLI 是可信操作员演示入口，教师、学生、教务员是业务职责称谓。

这些取舍适用于课程演示。若升级为实际教务系统，必须先重新确认学校政策，增加认证、授权、留痕、隐私保护及相应验证，不能直接把演示程序当作生产系统部署。

## 4. AI 辅助效果评价与反思

以下评价基于本项目采用的设计方法，讨论 AI 的作用和风险；它不声称学生已亲自完成所有审核、理解或运行测试。

AI 在需求结构化方面可以帮助整理角色、操作、流程、数据和约束，并把自然语言转换为实体与关系。本项目中，课程目录与实际教学班的区分、多对多联系的展开、约束清单与字段的对应，都是适合使用 AI 辅助起草的内容。但完整的表格并不意味着需求正确。学校是否允许重修、同一课程同学期是否只能选一个班、已出成绩后能否退课，都依赖实际业务政策。没有依据时，应该明确当前默认决定，避免把常见经验写成强制规则。

概念设计中的主要风险是实体边界和联系基数被过度简化。例如，如果把课程与教学班合成一个实体，就难以表达同课程多学期、多教师开班；如果为了图形完整而强造一对一实体，也会增加不必要的结构。AI 可以生成 Mermaid 图，但图中每条连线仍应由学生逐项解释，包括子侧必须关联一个父对象、父侧可以没有子对象，以及成绩为什么属于选课联系。能够生成图片或代码不能替代这种业务解释。

在逻辑设计中，AI 容易把“有主键”误当成“已经满足 3NF”，或因邮箱写了 `UNIQUE` 就直接称其为候选键。本设计要求逐表列出函数依赖和候选键闭包，针对联合主键证明非主属性是否依赖整个键，再检查非主属性间的传递依赖。人数缓存尤其需要区分：它是跨表聚合冗余，却不是教学班表内的“容量决定人数”。只看范式名称会漏掉真实的一致性问题；反过来把所有冗余都直接判为违反 3NF，也不严谨。

AI 生成 SQL 能减少重复录入，但语法看似合理不代表运行正确。外连接后误把条件放入 `WHERE`、对空班使用 `COUNT(*)`、在一对多连接后直接累加容量、简单平均多个班级平均分，都可能产生可执行但语义错误的结果。应准备可手算的小样本，对照查询输出，而不只检查数据库是否报错。字段范围、空值、唯一性和参照完整性也必须用合法与非法输入分别验证。

JDBC 方面，AI 可协助整理连接、参数化语句、结果读取和事务代码，但异常路径比正常路径更容易遗漏。只调用 `commit`，或捕获异常后不回滚，都可能留下不一致状态。当前还必须关注提交本身可能因延迟约束而失败，不能把成功执行 `UPDATE` 当作业务已提交。批量选课按教学班 ID 升序获取锁并整体回滚，有助于避免反向锁序。容量判断若只采用应用先读后写，即使单次演示正常，也不能说明并发安全。需要通过两个独立连接竞争最后名额，并在异常回滚后检查选课记录和人数缓存，才能对关键业务作出有证据的判断。

因此，AI 更适合生成候选方案、解释理论和组织检查清单，学生应承担最终判断与验证责任。真实理解应体现为能够说明为什么使用联合主键、为什么外键不级联删除、为什么两类空值含义不同、为什么无损分解需要判据，以及为什么跨表计数不能由普通函数依赖保证。若完全依赖 AI 并直接提交未经理解的结果，可能交付形式完整却不符合业务、并发下损坏数据、测试记录失真的系统。本项目的正式评价应在实际运行和人工复核后补充真实结果，不能预先写成“全部通过”。

## 5. 代表性风险示例与真实纠错记录要求

任务书要求至少两个真实 AI 错误或不合理结果，并记录发现、原因、修改与验证。当前没有足以证明两次真实纠错全过程的记录，以下仅为本项目相关的**风险示例和复核口径，不计作已完成的真实 AI 纠错案例**。

| 风险示例 | 为什么不合理 | 本项目采用的处理 | 应如何实际验证 |
|---|---|---|---|
| 将“可空且唯一的邮箱”直接列为学生候选键 | 允许多个学生邮箱为 `NULL`，不能唯一标识每个学生 | 候选键采用 `student_id` 和 `student_no`；邮箱只作可空唯一属性 | 插入不同学生且邮箱均为空应合法；重复非空邮箱应拒绝；学生解释候选键的最小性和完整覆盖 |
| 用“先 SELECT 剩余容量，再 INSERT”证明不会超选 | 并发事务可能同时读到同一个空位 | 由数据库触发器对教学班执行带容量条件的原子更新，同事务维护记录和人数 | 两个独立连接竞争最后一个名额；检查提交数、实际选课数和缓存人数 |
| 将人数缓存笼统判为违反 3NF，或用 3NF 宣称缓存必然正确 | 混淆表内 FD 与跨表聚合约束 | 分开说明范式与跨表冗余，维护触发器与提交时延迟约束共同保护，审计复核 | 学生复核 FD 推导，执行直接篡改提交拒绝、回滚及选退课后审计 |

正式记录应保留真实问题发生时的 Prompt、原回答或对应代码、发现问题的实际输入、原因分析、修改版本和修复后的实际输出，并能对应到成果位置。没有实际发生的错误不能作为历史事实补写，运行前的预期结果不能冒充实际结果。
