# 高校教学管理系统需求分析

## 1. 项目背景与边界

本项目依据根目录《大模型辅助数据库设计与JDBC编程_课程大作业》任务书，选择“高校教学管理系统”，使用 PostgreSQL 16、Java 17、pgJDBC 和命令行界面，演示从数据库设计到 JDBC 数据操作的完整过程。

系统以院系、学生、教师、课程、教学班、选课及成绩为对象。课程表示相对稳定的课程目录，教学班表示某门课程在某学期由一位教师承担的一次开设，成绩属于学生与教学班之间的选课记录。本项目采用六张核心表，不把业务角色额外建成用户账号表。

当前范围为独立课程原型：学生完整增删改查，两种多表报告，选课、退课、成绩录入事务，以及约束和并发验证。院系、教师、课程和教学班由初始化数据及 SQL 维护；不据此声称这些对象均已有完整 CLI 管理菜单。

不实现课表、上课时间、教室、先修课程、学分上限和登录认证。CLI 由可信操作员演示，业务角色说明不代表已实现身份验证或权限隔离。

## 2. 五个方面的需求分类

“明确需求”来自任务书或本项目已经确定的范围；“隐含需求”是实现明确需求所必需的一致性要求；“待确认”表示实际学校政策或提交条件尚无依据，当前采用表内说明的默认决定。

| 方面 | 明确需求 | 隐含需求 | 待确认事项与当前默认决定 |
|---|---|---|---|
| 用户角色 | 学生查看选课及成绩；教师查看授课和登记成绩；教务员维护基础信息、处理选退课及统计 | 角色操作最终需要落到确定的数据对象和事务边界；演示时操作员可代为执行 | 未给出账号、认证、授权方案；当前仅描述业务职责，不建立登录和角色权限系统 |
| 核心操作 | 学生 CRUD；至少两种多表报告；选课、退课、成绩录入 | 用参数化 SQL 处理输入；检查影响行数；失败回滚；关联学生不能直接删除 | 教师和课程完整 CLI CRUD 未列入本轮最低范围；当前用初始化 SQL 和数据库操作维护 |
| 业务流程 | 建立院系等基础资料、开设教学班、选课、退课、登记或查询成绩 | 重复选课要拒绝；容量不足要拒绝；名额判断和占用必须成为一个原子操作 | 尚无选课窗口、退课期限或已出成绩禁退政策；当前允许对存在的选课退课，删除记录及其成绩 |
| 核心数据 | 六表及其字段；学号、工号、课程代码、教学班代码等标识；人数和成绩 | 一门课可开多个教学班；未录入成绩应区别于零分；人数应等于实际选课数 | 未规定邮箱格式、大小写等价或成绩历史版本；当前邮箱可空且非空值唯一，成绩只保存当前值 |
| 业务规则与约束 | 主键、唯一、外键、非空、数值范围、学期格式、容量控制 | 防止并发超选；删除不得产生孤立记录；选课关系身份不可更改 | 未要求禁止重修或同课程同学期多班；当前均允许，仅禁止同一学生重复选择同一教学班 |

## 3. 业务角色与操作

| 业务角色 | 业务职责 | 原型中的对应操作 |
|---|---|---|
| 学生 | 查询课程与教学班，提出选退课请求，查询自己的成绩 | 操作员输入学生标识执行选退课；学生选课成绩明细报告 |
| 教师 | 查看所授教学班及名单，登记成绩 | 按教学班查询相关信息，针对已存在选课记录更新成绩 |
| 教务员 | 维护基础数据，核对学生资料，开班，统计人数和成绩 | 学生 CRUD、基础数据 SQL、教学班统计报告和一致性审计 |

上述职责没有数据库账号或 CLI 身份凭证作为强制边界。当前不能据此承诺学生只能查询本人、教师只能修改本人授课成绩，也不能把操作员输入的学生编号当作已认证的身份。

## 4. 核心业务流程与事务边界

### 4.1 基础资料与开班

1. 建立院系，再建立归属该院系的学生、教师和课程。
2. 为已有课程指定教师、学期和容量，创建教学班。
3. 新教学班人数默认为 0。基础资料被下游记录引用时，删除受 `ON DELETE RESTRICT` 限制；现有 SQL 未显式声明 `ON UPDATE`，采用默认 `NO ACTION`，同样不允许键更新造成悬空引用。

教师所属院系不要求等于课程所属院系；学生也可以选择其他院系开设的课程。这两项限制没有出现在既定需求中，不能凭字段名称自行添加。

### 4.2 学生资料维护

新增、按标识或条件查询、修改、删除构成完整 CRUD。主键用于稳定引用，学号作为业务候选键保持唯一。不存在的记录应返回“未找到”或零影响行数，不把空结果当成程序崩溃。

修改学生所属院系要检查目标院系存在。删除有选课记录的学生应由外键拒绝，不隐式清除成绩。演示删除正常流程应选择无选课记录的学生。

### 4.3 选课

1. JDBC 开启显式事务，使用 `PreparedStatement` 插入 `(student_id, class_id)`。批量选课先将教学班 ID 升序排列，再依序插入，使不同批次使用统一的教学班锁顺序。
2. 数据库触发器对目标教学班执行带容量条件的原子 `UPDATE`，仅在 `enrolled_count < capacity` 时加一。
3. 目标教学班不存在、容量不足、学生不存在或联合主键重复时，本次选课失败；任何已发生的人数变动须随失败语句或事务一起撤销。
4. 全部成功后 `commit`；任一教学班选课失败时，整批 `rollback`，撤销此前成功项。提交阶段的延迟计数约束也可能报错，必须纳入异常和回滚路径。

`trg_verify_enrollment_count` 是 `DEFERRABLE INITIALLY DEFERRED` 约束触发器，在事务提交时比对人数缓存和真实选课数。普通事务直接修改人数，即使值仍在 0 至容量之间，只要与明细不一致，也不能成功提交；一致性保护不只依赖操作员自律或权限约定。

不能用“先查询人数，再在 Java 中判断并插入”代替原子容量控制；两个并发连接可能同时读到最后一个空位。多人竞争同一班的末位名额时，成功提交人数不得超过剩余容量。

### 4.4 退课

按联合主键删除选课记录。数据库触发器在同一事务内将对应教学班人数减一；删除零行表示未选该班，不应额外减人数。记录中的当前成绩随该选课记录删除，当前不提供退课历史归档。

当前退课为自动提交模式下的单条 `DELETE`，该语句与人数触发器构成原子事务；失败时数据库撤销该语句的全部效果，避免“记录已删除但人数未减”或相反状态。重新选课生成新的选课时间，原成绩不自动恢复。

### 4.5 成绩录入

仅更新已存在选课记录的 `grade`，不得通过录分操作新建选课或更改 `student_id`、`class_id`。成绩只允许 `NULL` 或 0 至 100；`NULL` 表示尚未录入，`0.00` 表示已录入零分。当前录分为自动提交模式下的单条 `UPDATE`，非法输入导致该语句失败并撤销，目标记录不存在时应明确反馈。

当前允许修改或清空已有成绩，不提供成绩审批、修改留痕或多次考试记录。若学校要求保留成绩历史，需要单独设计业务流程和数据结构。

### 4.6 报告

报告一按学号展示学生、教学班、课程、教师及成绩，覆盖三张以上数据表。当前报告二展示教学班代码、课程、教师、容量、缓存选课人数和平均分；人数缓存由触发器及提交时一致性校验保护，另用审计查询核对真实条数。平均分只计算非空成绩；无选课、未录分和零分必须能被区分。已录成绩人数可由统计 SQL 获取，当前不将其写成 CLI 已有的输出字段。

## 5. 核心数据

| 表 | 数据含义 | 主标识及关键属性 |
|---|---|---|
| `departments` | 院系目录 | 院系 ID、代码、名称 |
| `students` | 学生学籍信息 | 学生 ID、学号、姓名、院系、可空邮箱、入学年份 |
| `teachers` | 教师基本信息 | 教师 ID、工号、姓名、院系 |
| `courses` | 课程目录 | 课程 ID、课程代码、课程名、学分、开课院系 |
| `teaching_classes` | 实际开设的教学班 | 教学班 ID、教学班代码、课程、教师、学期、容量、人数缓存 |
| `enrollments` | 学生与教学班的多对多关联 | 学生 ID 与教学班 ID 联合主键、选课时间、可空成绩 |

详细类型与候选键见《02_概念设计》和《03_逻辑设计与规范化》。所有字段除 `students.email`、`enrollments.grade` 外均为必填；所有字符串有长度上限并要求去除两端普通空格后非空。

## 6. 业务规则到约束的映射

| 编号 | 业务规则 | 落实位置与具体约束 |
|---|---|---|
| R01 | 每条实体记录有稳定标识 | 前五表 `bigint` identity 主键；选课表联合主键 `(student_id, class_id)` |
| R02 | 业务编号不重复 | `department_code`、`student_no`、`teacher_no`、`course_code`、`class_code` 各自 `UNIQUE NOT NULL` |
| R03 | 院系名称唯一，人员名和课程名可重名 | `department_name UNIQUE NOT NULL`；其余名称只有非空和长度约束 |
| R04 | 必填项和字符串不能为空 | 除邮箱、成绩外 `NOT NULL`；字符串 `CHECK (btrim(字段) <> '')`；邮箱用可空版本 |
| R05 | 学生邮箱可不填，填值后不重复 | `email varchar(120) UNIQUE` 且允许 `NULL`；`CHECK (email IS NULL OR btrim(email) <> '')` |
| R06 | 学生入学年份在范围内 | `admission_year smallint NOT NULL CHECK (admission_year BETWEEN 2000 AND 2100)` |
| R07 | 学分为正且不超过 10 | `credits numeric(3,1) NOT NULL CHECK (credits > 0 AND credits <= 10)` |
| R08 | 学期格式及学年有效 | `semester varchar(11) NOT NULL`；正则 `^[0-9]{4}-[0-9]{4}-[12]$` 并核对第二年等于第一年加一 |
| R09 | 教学班容量有限 | `capacity integer NOT NULL CHECK (capacity BETWEEN 1 AND 500)` |
| R10 | 人数非负且不超过容量 | `enrolled_count integer NOT NULL DEFAULT 0`，`CHECK (enrolled_count BETWEEN 0 AND capacity)` |
| R11 | 所属或引用对象必须存在 | 所有七条外键均为 `ON DELETE RESTRICT`；更新采用默认 `NO ACTION`，无级联删除 |
| R12 | 同一学生不能重复选择同一教学班 | `enrollments PRIMARY KEY (student_id, class_id)` |
| R13 | 选课有时间记录 | `enrolled_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| R14 | 成绩可未录入，录入后在 0 至 100 | `grade numeric(5,2)`，可空且 `CHECK (grade BETWEEN 0 AND 100)`；`NULL` 不视为 0 |
| R15 | 并发选课不能超容量 | 选课触发器的条件原子 `UPDATE`；锁和事务保护同一教学班的容量竞争 |
| R16 | 人数等于对应实际选课条数 | 选退课触发器维护；`trg_verify_enrollment_count` 延迟至提交核对真实 `COUNT(*)` 并拒绝差异；聚合审计用于复核，单表 `CHECK` 不能保证这一跨表等式 |
| R17 | 选课关系身份不能更新 | 数据库更新检查触发器拒绝改变 `student_id` 或 `class_id`；换班按事务退课后再选课 |
| R18 | 人数直接篡改不能以不一致状态提交 | 延迟约束触发器在提交时强制校验；CLI、DAO 无直接修改人数入口；最小权限可作后续增强，当前不声称真实权限系统已部署 |
| R19 | 业务失败不留下半完成数据 | 批量选课显式 `commit/rollback` 且按教学班 ID 升序执行；退课和录分利用单语句事务原子性；检查影响行数 |

`btrim` 非空检查不等于自动去空格，也不等于大小写不敏感。当前不承诺把 `CS` 和 `cs`、或带两端空格的不同值视为同一业务编号；CLI 可规范输入，但数据库唯一性的语义必须以实际字段和排序规则为准。后续若要求忽略大小写或标准化唯一性，需要明确业务口径后统一修改。

`numeric` 类型会按字段小数位表示存储值。当前数据库范围检查针对转换后的数值；若要求禁止输入过多小数位，需在录入边界额外拒绝，不能宣称已有 `CHECK` 自动校验了原始输入精度。

## 7. 数量与验收标准

| 验收项 | 可观察标准 |
|---|---|
| 数据规模 | 六张表分别至少 10 条记录；已确认初始化基线为院系 10、学生 20、教师 10、课程 10、教学班 12、选课 24；引用合法且计数一致 |
| SQL 查询 | 至少 8 条：单表条件 2、多表关联 2、分组及 `HAVING` 1、嵌套 2、复杂业务 1 |
| JDBC 功能 | 学生完整 CRUD；两种多表报告；选课、退课和成绩事务；参数化 SQL；常见异常处理 |
| 基础测试 | 至少 10 个真实执行的用例，覆盖正常、边界、重复、非法值、外键和回滚 |
| 并发测试 | 两个独立数据库连接竞争最后一个名额；最终成功提交至多一人且人数与记录一致 |
| 提交证据 | 实际运行结果、测试输入与预期/实际对照、必要截图、真实 AI 交互和人工审核说明 |

建库、初始化、八类查询、29 项自动化测试和并发争抢最后名额已于 2026-11-18 在本地 PostgreSQL 16.16 实际执行，结果见 `docs/05_测试报告.md` 与 `evidence/`。这些结果覆盖当前实现范围，不扩展为真实教务政策和生产环境已经验收；正式提交前仍须由学生亲自复核需求、解释设计并补充真实人工审核与组队信息。
