# 大模型辅助数据库设计与编程记录

## 1. 使用范围与提示词

本项目使用大模型辅助梳理需求、生成设计初稿、检查 SQL 和 JDBC 结构、整理文档。题目要求的参考提示词为：

> 你是一名具有丰富经验的数据库系统分析师。现在需要设计一个【项目名称】。请从数据库设计角度分析系统需求，包括：1. 系统涉及哪些用户角色？2. 每类用户有哪些核心操作？3. 系统涉及哪些业务流程？4. 需要管理哪些核心数据？5. 有哪些业务规则和数据完整性约束？请以结构化形式输出，并区分明确需求、隐含需求和需要进一步确认的需求。

在本项目中，该提示词被具体化为“高校教学管理系统”，并要求模型把需求分为明确需求、隐含需求和待确认事项。模型给出的初稿不是最终答案：课程与教学班是否分开、成绩归属哪个实体、人数是否缓存、并发如何保护，均经过数据库约束和实际测试重新核对。

## 2. AI 生成结果与人工取舍

AI 在以下环节提供了有效初稿：

- 将教务业务拆成院系、学生、教师、课程、教学班和选课六类核心数据。
- 识别“学生—教学班”的多对多联系，并把成绩和选课时间放入联系表。
- 生成 Mermaid E-R 图、候选键清单、函数依赖分析框架和八类查询的初稿。
- 生成 JDBC 的 `DBUtil`、DAO、Service 分层骨架，以及 `PreparedStatement`、事务和异常处理示例。

最终实现没有照搬“所有功能都由大模型决定”的做法。项目只承诺学生完整 CRUD、两种多表报告、选课退课成绩事务，不虚构教师和课程的完整 CLI 管理；不虚构登录认证和角色权限；不把常见教务政策写成未经确认的硬规则。未确认项在需求文档中列出当前默认决定，例如允许跨学期重修、允许同课程同学期选择不同教学班、退课不设时间窗。

## 3. 两个真实纠错记录

### 3.1 CLI 中文输出编码错误

**发现过程。** 第一次把命令行输出重定向到日志并以 UTF-8 读取时，菜单和查询结果出现乱码。此前的交互式窗口看起来正常，因此只靠肉眼没有暴露问题。

**原因。** Java 在 Windows 上按平台默认字符集创建 `System.out` 和 `Scanner`，重定向或 CI 环境按 UTF-8 读取时就不一致。问题不在数据库，也不在 SQL 查询结果。

**修改。** 在 `Main` 启动时用 UTF-8 包装标准输出和标准输入；运行脚本同时设置控制台与管道编码。新增 `CliTest`，启动真实 JVM、关闭输入并断言 UTF-8 输出包含中文菜单。

**验证。** 修复前测试失败，输出中的中文无法按 UTF-8 解码；修复后 `CliTest` 两项通过，完整测试为 29 项全部通过。对应证据在 `evidence/test-output.txt`。

### 3.2 外键更新策略的文档与 DDL 不一致

**发现过程。** 物理设计初稿写了“七条外键均显式采用 `ON DELETE RESTRICT ON UPDATE RESTRICT`”，但实际 `sql/create_tables.sql` 只写了 `ON DELETE RESTRICT`，`ON UPDATE` 使用 PostgreSQL 默认的 `NO ACTION`。

**原因。** `RESTRICT` 与 `NO ACTION` 在本项目这种非延迟普通外键上行为接近，但二者不是同一个显式声明；把默认行为写成已显式配置，属于文档与实现不一致。若后续改成延迟约束，两者差异还会影响检查时机。

**修改。** 保留 DDL 的 `ON DELETE RESTRICT` 和默认 `ON UPDATE NO ACTION`，不为了迎合文字而修改已工作的实现；需求、逻辑设计、物理设计和总结统一写成“删除使用 `RESTRICT`，更新使用默认 `NO ACTION`”。选课身份字段另有触发器禁止原地改键。

**验证。** 用 `rg` 对照三份设计文档和建表脚本；删除被引用学生、引用不存在院系的测试分别返回 `23503`。该项是设计一致性修正，不伪称为数据库运行错误。

## 4. AI 辅助效果评价

大模型对需求结构化和初稿生成帮助明显。它能较快把“教务管理”拆成角色、流程、数据和规则，并给出 E-R 图、关系模式和 JDBC 分层的可讨论起点，减少从空白页开始的成本。对于课程设计这类边界相对清楚的题目，这种起草价值主要体现在覆盖面：角色是否遗漏、联系属性是否放错、查询类型是否齐全，都可以先用清单检查。

但模型生成的内容不能直接作为正确性证据。概念设计上，模型容易把“课程”和“教学班”合并，导致同一课程多学期、多教师开班无法表达；也可能为了图形好看强行制造一对一联系。本项目保留课程目录和教学班两层，并明确学生与教学班的多对多联系由选课表承载，成绩属于选课联系而不是学生或教学班实体。每条联系的基数、可选性和属性归属都需要回到业务语义解释，不能只看图是否完整。

逻辑设计上，模型常见的错误是把“有主键”当成“已经满足 3NF”，或者把可空唯一邮箱直接当作候选键。邮箱允许多个 `NULL`，不能唯一标识全体学生；本项目只把 `student_id` 和 `student_no` 作为学生候选键。人数缓存也不是简单的表内函数依赖：它等于选课明细的跨表计数，教学班表可以满足 3NF，同时仍需要触发器和提交时校验来维护一致性。把这两件事混为一谈，是只看范式标签就会漏掉的问题。

SQL 方面，模型能生成可读的建表、查询和 JDBC 代码，但“能执行”不等于“结果正确”。外连接后把条件写进 `WHERE`、用 `COUNT(*)` 统计空班、在展开的选课明细上直接累加容量，都会产生语法正确但业务错误的查询。本项目用可手算的种子数据和实际输出核对八类查询，并用非法输入验证唯一性、外键、范围和空值约束。对于并发容量，应用层“先查剩余再插入”不足以证明安全；最终采用数据库触发器中的条件原子更新，并用两个独立连接争抢最后一个名额验证。

JDBC 方面，模型给出的正常路径通常完整，异常路径更容易遗漏。只 `commit` 不回滚、把 `UPDATE` 成功当作业务成功、提交时忽略延迟约束失败，都会留下不一致状态。本项目在批量选课中显式 `commit/rollback`，按教学班 ID 排序降低反向锁序风险，检查影响行数，并把常见 SQLState 转换为可读提示；但发生序列化失败或死锁时只提示重试，不静默自动重复提交。

因此，AI 适合做需求清单、初稿、代码骨架和检查提醒，不适合替代学生对业务政策、函数依赖、事务边界和测试结果的最终判断。若完全依赖模型并直接提交，最可能的后果不是“代码跑不起来”，而是系统能演示却违反真实政策、在并发下超选、文档与 DDL 不一致，或者测试记录无法对应实际运行。本项目保留真实执行输出、测试结果和纠错记录，同时明确尚未完成的学生人工复核与正式组队信息。
